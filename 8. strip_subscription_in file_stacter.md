# Reference Notes — Premium Content + Stripe Subscription Module

> Format: folder/filename → code → flowchart → short explanation, repeated per file. Personal reference for re-implementing this pattern correctly in a future project.

---

## Naming rule (check this first, always)

**Folder name → file prefix → import path → exported variable name must be the exact same string, every time.** The original code this doc is based on had three spellings of the same module (`premium`, `premimum`, `premimu`) across the folder and its own imports — that crashes on `Cannot find module` the instant it runs. Every file below uses the corrected, consistent name, not the typo'd originals. This rule also caught a second mismatch this round: the guard middleware file was named `premiumGuard.ts` but its own export inside was called `subscriptionGuard` — renamed the **file** to `subscriptionGuard.ts` below, since the export name is what every other file actually imports by.

## The Big Picture First — How Subscribing Actually Unlocks Premium Content

This is the part worth understanding before any individual file — three separate pieces have to work together, and it's easy to lose track of which piece is responsible for what.

```
┌─────────────────────────────────────────────────────────────────────┐
│  STEP 1 — User subscribes                                              │
│  POST /subscription/checkout  →  createCheckoutSession()                │
│  → Stripe hosted checkout page → user pays with card                     │
└─────────────────────────────────────────────────────────────────────┘
                                      │
                                      ▼
┌─────────────────────────────────────────────────────────────────────┐
│  STEP 2 — Stripe confirms payment via webhook (NOT the browser redirect) │
│  POST /subscription/webhook  →  handlewebhook()                          │
│  → verifies signature → checkout.session.completed                        │
│  → handleCheckoutCompleted() WRITES the Subscription row to your DB         │
│    { userId, status: "ACTIVE", currentPeriodEnd }                            │
└─────────────────────────────────────────────────────────────────────┘
                                      │
                              (this is the moment the user
                               actually becomes "subscribed",
                               nothing before this counts)
                                      ▼
┌─────────────────────────────────────────────────────────────────────┐
│  STEP 3 — Later, the user requests premium content                       │
│  GET /premium  →  auth()  →  subscriptionGuard()  →  controller             │
│  subscriptionGuard READS the same Subscription row STEP 2 wrote               │
│  → status === "ACTIVE"? → next() : throw 403                                  │
└─────────────────────────────────────────────────────────────────────┘
                                      │
                                      ▼
┌─────────────────────────────────────────────────────────────────────┐
│  STEP 4 — If a subscription is later canceled or expires                 │
│  Stripe sends customer.subscription.updated / .deleted                     │
│  → handleChangeSubscription() UPDATES that same row's status                │
│  → next time subscriptionGuard reads it, access is revoked automatically     │
└─────────────────────────────────────────────────────────────────────┘
```

**The one sentence version:** the webhook handler is the only place that ever *writes* subscription status, and `subscriptionGuard` is the only place that ever *reads* it to make an access decision — every other piece of code just moves data between those two. If access isn't behaving correctly, the bug is in one of those two spots, not anywhere else.

## `subscription/subscription.route.ts`

```ts
import { Router } from "express";
import { subscriptionController } from "./subscription.controller";
import { auth } from "../../middlewares/auth";
import { Role } from "../../../generated/prisma/enums";

const router = Router();

router.post(
  "/checkout",
  auth(Role.USER, Role.AUTHOR, Role.ADMIN),
  subscriptionController.createCheckoutSession,
);

router.post("/webhook", subscriptionController.handleWebhook)
router.get("/status", auth(Role.USER, Role.AUTHOR, Role.ADMIN), subscriptionController.getSubscriptionStatus)

export const subscriptionRoutes = router;
```

```
POST /subscription/checkout ──> auth() ──> createCheckoutSession
POST /subscription/webhook  ──────────────> handleWebhook   (no auth — Stripe calls this, not a logged-in user)
GET  /subscription/status   ──> auth() ──> getSubscriptionStatus
```

**Short explanation:** Three distinct routes with different purposes. Note `/webhook` deliberately has **no** `auth()` — Stripe's servers call this endpoint directly, they don't have a login token for your app. Instead, this route's real protection is the signature verification that happens inside the service (see `handlewebhook` below) — that's what proves the request genuinely came from Stripe.

## `subscription/subscription.controller.ts`

```ts
import { NextFunction, Request, Response } from "express"
import { catchAsync } from "../../utils/catchAsync"
import { subscriptionService } from "./subscription.service";
import { sendResponse } from "../../utils/sendResponse";
import httpStatus from "http-status"

const createCheckoutSession = catchAsync(async (req: Request, res: Response, next: NextFunction) => {
  const userId = req.user?.id;

  const result = await subscriptionService.createCheckoutSession(userId as string)
  sendResponse(res, {
    success: true,
    statusCode: httpStatus.OK,
    message: "Checkout session created successfully",
    data: result
  })
})

const handleWebhook = catchAsync(async (req: Request, res: Response, next: NextFunction) => {
  const event = req.body as Buffer
  const signature = req.headers['stripe-signature']!;
  await subscriptionService.handlewebhook(event, signature as string)

  sendResponse(res, {
    success: true,
    statusCode: httpStatus.OK,
    message: "Webhook processed successfully",
    data: {}
  })
})

const getSubscriptionStatus = catchAsync(async (req: Request, res: Response, next: NextFunction) => {
  const userId = req.user?.id

  const result = await subscriptionService.getSubscriptionStatus(userId as string)
  sendResponse(res, {
    success: true,
    statusCode: httpStatus.OK,
    message: "Subscription status retrieved successfully",
    data: result
  })
})

export const subscriptionController = {
  createCheckoutSession,
  handleWebhook,
  getSubscriptionStatus
}
```

```
createCheckoutSession(req,res)
     │
     ▼
subscriptionService.createCheckoutSession(userId)
     │
     ▼
sendResponse → { paymentUrl }

handleWebhook(req,res)
     │
     ▼
subscriptionService.handlewebhook(rawBody, signature)
     │
     ▼
sendResponse → {}

getSubscriptionStatus(req,res)
     │
     ▼
subscriptionService.getSubscriptionStatus(userId)
     │
     ▼
sendResponse → { status, currentPeriodEnd, ... }
```

**Short explanation:** Three thin wrappers, same pattern used everywhere else — pull whatever the request needs (`userId` from `req.user`, or the raw body + Stripe signature header for the webhook), hand it to the service, format the result. Original had `getSubscriptionStatus` return `data: { result }` (nested) while `createCheckoutSession` returns `data: result` (flat) — flattened here for consistency.

## `subscription/subscription.service.ts`

```ts
import Stripe from "stripe";
import config from "../../config";
import { prisma } from "../../lib/prisma";
import { stripe } from "../../lib/stripe";
import { SubscriptionStatus } from "../../../generated/prisma/enums";
import { handleChangeSubscription, handleCheckoutCompleted } from "./subscription.utils";

const createCheckoutSession = async (userId: string) => {
  const transactionResult = await prisma.$transaction(async (tx) => {
    const user = await tx.user.findUniqueOrThrow({
      where: { id: userId },
      include: { subscription: true },
    });

    // returning subscriber — reuse their existing Stripe customer
    let stripeCustomerId = user.subscription?.stripeCustomerId;

    // new subscriber — create a Stripe customer for them
    if (!stripeCustomerId) {
      const customer = await stripe.customers.create({
        email: user.email,
        name: user.name,
        metadata: { userId: user.id },
      });
      stripeCustomerId = customer.id;
    }

    const session = await stripe.checkout.sessions.create({
      line_items: [{ price: config.stripe_product_id, quantity: 1 }],
      mode: "subscription",
      customer: stripeCustomerId,
      payment_method_types: ["card"],
      success_url: `${config.app_url}/premium?success=true`,
      cancel_url: `${config.app_url}/payment?success=false`,
      metadata: { userId: user.id },
    });
    return session.url;
  });
  return { paymentUrl: transactionResult };
};
```
```
┌──────────────┐   POST /checkout    ┌──────────────┐
│  Frontend         │ ─────────────────────> │  createCheckoutSession│
│  "Subscribe"        │                          │                             │
└──────────────┘                          └──────────────┘
                                                        │
                                                        ▼
                                           ┌──────────────┐
                                           │  Does user already   │
                                           │  have a Stripe          │
                                           │  customer ID?             │
                                           └──────────────┘
                                              │yes         │no
                                              ▼               ▼
                                        reuse it     stripe.customers.create()
                                              │               │
                                              └──────┬──────┘
                                                       ▼
                                           ┌──────────────┐
                                           │  stripe.checkout.        │
                                           │  sessions.create()          │
                                           │  metadata.userId = ...       │
                                           └──────────────┘
                                                       │
                                                       ▼
                                           ┌──────────────┐
                                           │  return session.url,     │
                                           │  frontend redirects       │
                                           │  browser there                │
                                           └──────────────┘
```
**Short explanation:** `metadata: { userId: user.id }` is stamped on both the Stripe customer *and* the checkout session — Stripe has no concept of your own user IDs, so this is how you later recognize, inside a webhook event, which of *your* users the event is about.

```ts
const handlewebhook = async (payload: Buffer, signature: string) => {
  const endpointsecret = config.stripe_webhook_secret;
  const event = stripe.webhooks.constructEvent(payload, signature, endpointsecret);

  switch (event.type) {
    case "checkout.session.completed": {
      const session = event.data.object;
      await handleCheckoutCompleted(session);
      break;
    }
    case "customer.subscription.updated": {
      const subscription = event.data.object;
      await handleChangeSubscription(subscription);
      break;
    }
    case "customer.subscription.deleted": {
      const subscription = event.data.object;
      await handleChangeSubscription(subscription);
      break;
    }
    default:
      break;
  }
};
```
```
┌──────────────┐
│  Stripe sends webhook  │
│  raw body + signature   │
└──────────────┘
              │
              ▼
┌──────────────┐        wrong        ┌──────────────┐
│  If express.json()        │ ─────────────────> │  Signature verify FAILS │
│  parsed the body first      │                      │  (needs raw bytes)          │
└──────────────┘                      └──────────────┘
              │
        (must be raw)
              ▼
┌──────────────┐
│  stripe.webhooks.               │
│  constructEvent() — verifies      │
│  this really came from Stripe       │
└──────────────┘
              │
              ▼
┌──────────────┐
│  switch(event.type)                │
├──────────────┤
│ checkout.session.completed  ──> handleCheckoutCompleted()  ← WRITES subscription for the first time
│ customer.subscription.updated ─> handleChangeSubscription()  ← UPDATES existing subscription
│ customer.subscription.deleted ─> handleChangeSubscription()  ← UPDATES status to expired/canceled
│ (anything else)             ──> ignored
└──────────────┘
```
**Short explanation:** `payload` **must** be the raw, unparsed request body — this route needs `express.raw({ type: "application/json" })` instead of the normal JSON body parser, registered before any global `express.json()`, or signature verification will always fail and Stripe will retry forever without ever succeeding. This is the single function responsible for every write to the `Subscription` table — everything downstream (including `subscriptionGuard`, further down) only ever reads what this function wrote.

```ts
const getSubscriptionStatus = async (userId: string) => {
  const isSubscriptionExist = await prisma.subscription.findFirstOrThrow({
    where: { userId }
  })
  const isActive = isSubscriptionExist.status === "ACTIVE"
    && isSubscriptionExist.currentPeriodEnd
    && new Date(isSubscriptionExist.currentPeriodEnd) > new Date();

  return {
    status: isSubscriptionExist.status,
    isActive,
    currentPeriodEnd: isSubscriptionExist.currentPeriodEnd
  }
}

export const subscriptionService = {
  createCheckoutSession,
  handlewebhook,
  getSubscriptionStatus
};
```
```
┌──────────────┐
│  getSubscriptionStatus(  │
│    userId )                       │
└──────────────┘
              │
              ▼
┌──────────────┐
│  find this user's             │
│  Subscription row               │
└──────────────┘
              │
              ▼
┌──────────────┐        no         ┌──────────────┐
│  status === "ACTIVE"?    │ ────────────────> │  isActive = false     │
└──────────────┘                     └──────────────┘
              │ yes
              ▼
┌──────────────┐        no         ┌──────────────┐
│  currentPeriodEnd is        │ ────────────────> │  isActive = false     │
│  still in the future?         │                     └──────────────┘
└──────────────┘
              │ yes
              ▼
┌──────────────┐
│  isActive = true               │
└──────────────┘
```
**Short explanation:** Both conditions are required, not just the status string. When a user cancels, Stripe doesn't revoke access instantly — they've already paid for the current period, so `status` alone might still say something ambiguous while a cancellation is pending. Checking the actual date is what correctly keeps access open until the period they already paid for ends. This is a **user-facing status check** ("what does my account currently show") — different purpose from `subscriptionGuard` below, which is an **access-control gate** blocking a route entirely. They happen to use near-identical logic, which is exactly why the guard is worth building as its own reusable middleware rather than copy-pasting this same condition into every protected route.

## `subscription/subscription.utils.ts`

```ts
import Stripe from "stripe";

export const getPeriodEnd = (payload: Stripe.Subscription) => {
  const currentPeriodEndInMilliseconds = payload.items.data[0]?.current_period_end!;
  const currentPeriodEnd = new Date(currentPeriodEndInMilliseconds * 1000);
  return currentPeriodEnd;
};
```
```
┌──────────────┐
│  Stripe subscription       │
│  current_period_end            │
│  (Unix seconds)                   │
└──────────────┘
              │
              ▼   × 1000
┌──────────────┐
│  JS Date object                    │
│  (needs milliseconds)          │
└──────────────┘
```
**Short explanation:** The entire function is one unit conversion. Stripe timestamps are seconds since epoch; JavaScript's `Date` constructor expects milliseconds. Forgetting this `* 1000` is one of the most common Stripe-integration bugs — dates would be wildly wrong (year ~1970-something) instead of erroring loudly, which makes it easy to miss in testing.

```ts
export const handleCheckoutCompleted = async (session: Stripe.Checkout.Session) => {
  const userId = session.metadata?.userId;
  const stripeCustomerId = session.customer as string;
  const stripeSubscriptionId = session.subscription as string;

  if (!userId || !stripeCustomerId || !stripeSubscriptionId) {
    console.log("webhook: missing values for checkout session");
    return;
  }

  const stripeSubscription = await stripe.subscriptions.retrieve(stripeSubscriptionId);
  const currentPeriodEnd = getPeriodEnd(stripeSubscription);

  await prisma.subscription.upsert({
    where: { userId },
    create: { userId, stripeCustomerId, stripeSubscriptionId, status: "ACTIVE", currentPeriodEnd },
    update: { stripeCustomerId, stripeSubscriptionId, status: "ACTIVE", currentPeriodEnd },
  });
};
```
```
┌──────────────┐
│  checkout.session.completed  │
│  event received                    │
└──────────────┘
              │
              ▼
┌──────────────┐        missing      ┌──────────────┐
│  userId / customerId /    │ ─────────────────> │  log + bail out early   │
│  subscriptionId present?     │                       └──────────────┘
└──────────────┘
              │ all present
              ▼
┌──────────────┐
│  fetch full subscription       │
│  details from Stripe              │
└──────────────┘
              │
              ▼
┌──────────────┐        exists      ┌──────────────┐
│  Does a Subscription       │ ─────────────────> │  UPDATE that row            │
│  row for this userId          │                       └──────────────┘
│  already exist?                    │
└──────────────┘        doesn't exist
              │ ──────────────────────────────> ┌──────────────┐
                                                       │  CREATE a new row         │
                                                       └──────────────┘
```
**Short explanation:** This is where a subscription first actually gets written to your database — the checkout redirect (`success_url`) is purely cosmetic for the browser, this webhook handler is what really activates access. `upsert` (update-or-insert) handles both "brand new subscriber" and "resubscribing after a previous cancellation" with one call instead of an if/else.

```ts
export const handleChangeSubscription = async (payload: Stripe.Subscription) => {
  const stripeSubscriptionId = payload.id;
  const status =
    payload.status === "active" || payload.status === "trialing" ? SubscriptionStatus.ACTIVE
    : payload.status === "canceled" ? SubscriptionStatus.CANCELED
    : SubscriptionStatus.EXPIRED;

  const currentPeriodEnd = getPeriodEnd(payload);

  const isSubscriptionExist = await prisma.subscription.findUnique({
    where: { stripeSubscriptionId },
  });

  if (!isSubscriptionExist) {
    console.log(`webhook: no subscription found for id: ${stripeSubscriptionId}`);
    return;
  }

  await prisma.subscription.update({
    where: { stripeSubscriptionId },
    data: { status, currentPeriodEnd },
  });
};
```
```
┌──────────────┐
│  subscription.updated /      │
│  subscription.deleted event      │
└──────────────┘
              │
              ▼
┌──────────────┐
│  translate Stripe's own          │
│  status string → your own          │
│  SubscriptionStatus enum             │
└──────────────┘
              │
              ▼
┌──────────────┐        not found    ┌──────────────┐
│  find the matching        │ ─────────────────> │  log + bail out               │
│  row by stripeSubscriptionId  │                     └──────────────┘
└──────────────┘
              │ found
              ▼
┌──────────────┐
│  UPDATE status +                    │
│  currentPeriodEnd                      │
└──────────────┘
```
**Short explanation:** The status-translation step is deliberate insulation — your database's enum doesn't have to match Stripe's exact vocabulary, so if Stripe adds a new status string later, only this one function needs updating. This is the function that makes cancellation actually take effect: once it updates `status` away from `"ACTIVE"`, the very next check `subscriptionGuard` performs (below) will correctly deny access — no separate "revoke access" step needed anywhere else.

## `middlewares/subscriptionGuard.ts`

*(Renamed from `premiumGuard.ts` — the export inside was always called `subscriptionGuard`, so the file now matches it, per the naming rule.)*

```ts
import { NextFunction, Request, Response } from "express";
import { SubscriptionStatus } from "../../generated/prisma/enums";
import { prisma } from "../lib/prisma";
import { catchAsync } from "../utils/catchAsync";
import { AppError } from "../utils/AppError";

export const subscriptionGuard = () => {
  return catchAsync(async (req: Request, res: Response, next: NextFunction) => {
    const userId = req.user?.id;

    const subscription = await prisma.subscription.findUnique({
      where: { userId },
    });

    if (!subscription) {
      throw new AppError("Please subscribe to get access to premium content", 403);
    }

    if (subscription.status !== SubscriptionStatus.ACTIVE) {
      throw new AppError("Please renew your subscription to get access to premium content", 403);
    }

    next();
  });
};
```

```
┌─────────────────────┐
│  Request arrives,             │
│  already past auth()             │
│  (so req.user exists)              │
└─────────────────────┘
          │
          ▼
┌─────────────────────┐
│  Look up Subscription       │
│  row for this userId            │
└─────────────────────┘
          │
          ▼
┌─────────────────────┐    no row found    ┌──────────────────────┐
│  Does a subscription        │ ─────────────────────> │  403 — "Please             │
│  row exist at all?             │                          │  subscribe to get         │
└─────────────────────┘                          │  access"                    │
          │ row exists                          └──────────────────────┘
          ▼
┌─────────────────────┐   not ACTIVE     ┌──────────────────────┐
│  status === ACTIVE?         │ ─────────────────────> │  403 — "Please renew       │
└─────────────────────┘                        │  your subscription"        │
          │ ACTIVE
          ▼
┌─────────────────────┐
│  next() — request continues   │
│  through to the controller       │
└─────────────────────┘
```

**Short explanation:** Two separate rejection cases, deliberately worded differently for the user's benefit: **"no row at all"** means they've never subscribed (send them to the checkout flow), while **"row exists but not ACTIVE"** means they subscribed once and it lapsed or was canceled (send them to a renewal flow, not a first-time signup). **Fixed from the original:** the pasted version threw a bare `new Error(...)`, which has no `statusCode` attached — your `globalErrorHandler` would have no way to know this should be a `403 Forbidden` and would likely fall back to a generic `500`, which is semantically wrong (this isn't a server malfunction, it's an expected, correct rejection). Using `AppError(message, 403)` here — the same class used throughout the rest of the codebase — ensures the right status code reaches the client.

**Short explanation:** This is the corrected, fully-wired version — the original pasted `premium.router.ts` only had `auth()` and never actually called `subscriptionGuard()`, meaning *any* logged-in user could reach premium content regardless of subscription status.
