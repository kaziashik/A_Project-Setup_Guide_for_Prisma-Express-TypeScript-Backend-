


# Reference Notes — Premium Content + Stripe Subscription Module

> Format: folder/filename → code → flowchart → short explanation, repeated per file. Personal reference for re-implementing this pattern correctly in a future project.

---

## Naming rule (check this first, always)

**Folder name → file prefix → import path → exported variable name must be the exact same string, every time.** The original code this doc is based on had three spellings of the same module (`premium`, `premimum`, `premimu`) across the folder and its own imports — that crashes on `Cannot find module` the instant it runs. Every file below uses the corrected, consistent name (`premium`, `subscription`), not the typo'd originals.

## `premium/premium.router.ts`

```ts
import { Router } from "express"
import { auth } from "../../middlewares/auth"
import { premiumController } from "./premium.controller"
import { Role } from "../../../generated/prisma/enums"

const router = Router()

router.get("/", auth(Role.ADMIN, Role.AUTHOR, Role.USER), premiumController.getPremiumContent)

export const premiumRoutes = router
```

```
┌─────────────────────┐
│  GET /premium           │
└─────────────────────┘
          │
          ▼
┌─────────────────────┐        fails        ┌──────────────────────┐
│  auth(ADMIN,AUTHOR,      │ ──────────────────> │  401 Unauthorized       │
│  USER) — is anyone         │                      │  (not logged in)          │
│  logged in at all?           │                      └──────────────────────┘
└─────────────────────┘
          │ passes
          ▼
┌─────────────────────┐
│  premiumController.       │
│  getPremiumContent          │
└─────────────────────┘
```

**Short explanation:** One route, gated by `auth()`. Passing all three existing roles (`ADMIN, AUTHOR, USER`) means "any logged-in user" — functionally identical to calling `auth()` with no arguments in a system where those are the only three roles. Worth simplifying unless a future role should be excluded from this route specifically.

## `subscription/subscription.route.ts`

```ts
import { Router } from "express";
import { subscriptionController } from "./subscription.controller";
import { auth } from "../../middlewares/auth";
import { Role } from "../../../generated/prisma/enums";

const router = Router();

router.post(
  "/checkout",
  auth(Role.USER, Role.AUTHOR, Role.ADMIN),
  subscriptionController.createCheckoutSession,
);

router.post("/webhook", subscriptionController.handleWebhook)
router.get("/status", auth(Role.USER, Role.AUTHOR, Role.ADMIN), subscriptionController.getSubscriptionStatus)

export const subscriptionRoutes = router;
```

```
POST /subscription/checkout ──> auth() ──> createCheckoutSession
POST /subscription/webhook  ──────────────> handleWebhook   (no auth — Stripe calls this, not a logged-in user)
GET  /subscription/status   ──> auth() ──> getSubscriptionStatus
```

**Short explanation:** Three distinct routes with different purposes. Note `/webhook` deliberately has **no** `auth()` — Stripe's servers call this endpoint directly, they don't have a login token for your app. Instead, this route's real protection is the signature verification that happens inside the service (see `handlewebhook` below) — that's what proves the request genuinely came from Stripe.

## `subscription/subscription.controller.ts`

```ts
import { NextFunction, Request, Response } from "express"
import { catchAsync } from "../../utils/catchAsync"
import { subscriptionService } from "./subscription.service";
import { sendResponse } from "../../utils/sendResponse";
import httpStatus from "http-status"

const createCheckoutSession = catchAsync(async (req: Request, res: Response, next: NextFunction) => {
  const userId = req.user?.id;

  const result = await subscriptionService.createCheckoutSession(userId as string)
  sendResponse(res, {
    success: true,
    statusCode: httpStatus.OK,
    message: "Checkout session created successfully",
    data: result
  })
})

const handleWebhook = catchAsync(async (req: Request, res: Response, next: NextFunction) => {
  const event = req.body as Buffer
  const signature = req.headers['stripe-signature']!;
  await subscriptionService.handlewebhook(event, signature as string)

  sendResponse(res, {
    success: true,
    statusCode: httpStatus.OK,
    message: "Webhook processed successfully",
    data: {}
  })
})

const getSubscriptionStatus = catchAsync(async (req: Request, res: Response, next: NextFunction) => {
  const userId = req.user?.id

  const result = await subscriptionService.getSubscriptionStatus(userId as string)
  sendResponse(res, {
    success: true,
    statusCode: httpStatus.OK,
    message: "Subscription status retrieved successfully",
    data: result
  })
})

export const subscriptionController = {
  createCheckoutSession,
  handleWebhook,
  getSubscriptionStatus
}
```

```
createCheckoutSession(req,res)
     │
     ▼
subscriptionService.createCheckoutSession(userId)
     │
     ▼
sendResponse → { paymentUrl }

handleWebhook(req,res)
     │
     ▼
subscriptionService.handlewebhook(rawBody, signature)
     │
     ▼
sendResponse → {}

getSubscriptionStatus(req,res)
     │
     ▼
subscriptionService.getSubscriptionStatus(userId)
     │
     ▼
sendResponse → { status, currentPeriodEnd, ... }
```

**Short explanation:** Three thin wrappers, same pattern as `premium.controller.ts` — pull whatever the request needs (`userId` from `req.user`, or the raw body + Stripe signature header for the webhook), hand it to the service, format the result. Note: the original snippet had `getSubscriptionStatus` return `data: { result }` (nested) while `createCheckoutSession` returns `data: result` (flat) — fixed to flat here for consistency; pick one shape and keep every endpoint the same.

## `subscription/subscription.service.ts`

```ts
import Stripe from "stripe";
import config from "../../config";
import { prisma } from "../../lib/prisma";
import { stripe } from "../../lib/stripe";
import { SubscriptionStatus } from "../../../generated/prisma/enums";
import { handleChangeSubscription, handleCheckoutCompleted } from "./subscription.utils";

const createCheckoutSession = async (userId: string) => {
  const transactionResult = await prisma.$transaction(async (tx) => {
    const user = await tx.user.findUniqueOrThrow({
      where: { id: userId },
      include: { subscription: true },
    });

    // returning subscriber — reuse their existing Stripe customer
    let stripeCustomerId = user.subscription?.stripeCustomerId;

    // new subscriber — create a Stripe customer for them
    if (!stripeCustomerId) {
      const customer = await stripe.customers.create({
        email: user.email,
        name: user.name,
        metadata: { userId: user.id },
      });
      stripeCustomerId = customer.id;
    }

    const session = await stripe.checkout.sessions.create({
      line_items: [{ price: config.stripe_product_id, quantity: 1 }],
      mode: "subscription",
      customer: stripeCustomerId,
      payment_method_types: ["card"],
      success_url: `${config.app_url}/premium?success=true`,
      cancel_url: `${config.app_url}/payment?success=false`,
      metadata: { userId: user.id },
    });
    return session.url;
  });
  return { paymentUrl: transactionResult };
};
```
```
┌──────────────┐   POST /checkout    ┌──────────────┐
│  Frontend         │ ─────────────────────> │  createCheckoutSession│
│  "Subscribe"        │                          │                             │
└──────────────┘                          └──────────────┘
                                                        │
                                                        ▼
                                           ┌──────────────┐
                                           │  Does user already   │
                                           │  have a Stripe          │
                                           │  customer ID?             │
                                           └──────────────┘
                                              │yes         │no
                                              ▼               ▼
                                        reuse it     stripe.customers.create()
                                              │               │
                                              └──────┬──────┘
                                                       ▼
                                           ┌──────────────┐
                                           │  stripe.checkout.        │
                                           │  sessions.create()          │
                                           │  metadata.userId = ...       │
                                           └──────────────┘
                                                       │
                                                       ▼
                                           ┌──────────────┐
                                           │  return session.url,     │
                                           │  frontend redirects       │
                                           │  browser there                │
                                           └──────────────┘
```
**Short explanation:** `metadata: { userId: user.id }` is stamped on both the Stripe customer *and* the checkout session — Stripe has no concept of your own user IDs, so this is how you later recognize, inside a webhook event, which of *your* users the event is about. The `$transaction` wrapper here only protects the *read* (`findUniqueOrThrow`) since no database write happens in this function — the actual write happens later, in the webhook.

```ts
const handlewebhook = async (payload: Buffer, signature: string) => {
  const endpointsecret = config.stripe_webhook_secret;
  const event = stripe.webhooks.constructEvent(payload, signature, endpointsecret);

  switch (event.type) {
    case "checkout.session.completed": {
      const session = event.data.object;
      await handleCheckoutCompleted(session);
      break;
    }
    case "customer.subscription.updated": {
      const subscription = event.data.object;
      await handleChangeSubscription(subscription);
      break;
    }
    case "customer.subscription.deleted": {
      const subscription = event.data.object;
      await handleChangeSubscription(subscription);
      break;
    }
    default:
      break;
  }
};
```
```
┌──────────────┐
│  Stripe sends webhook  │
│  raw body + signature   │
└──────────────┘
              │
              ▼
┌──────────────┐        wrong        ┌──────────────┐
│  If express.json()        │ ─────────────────> │  Signature verify FAILS │
│  parsed the body first      │                      │  (needs raw bytes)          │
└──────────────┘                      └──────────────┘
              │
        (must be raw)
              ▼
┌──────────────┐
│  stripe.webhooks.               │
│  constructEvent() — verifies      │
│  this really came from Stripe       │
└──────────────┘
              │
              ▼
┌──────────────┐
│  switch(event.type)                │
├──────────────┤
│ checkout.session.completed  ──> handleCheckoutCompleted()
│ customer.subscription.updated ─> handleChangeSubscription()
│ customer.subscription.deleted ─> handleChangeSubscription()
│ (anything else)             ──> ignored
└──────────────┘
```
**Short explanation:** `payload` **must** be the raw, unparsed request body — this route needs `express.raw({ type: "application/json" })` instead of the normal JSON body parser, registered before any global `express.json()`, or signature verification will always fail and Stripe will retry forever without ever succeeding. The three event types handled here cover: first successful payment, any change to an existing subscription, and final removal after cancellation's grace period ends.

```ts
const getSubscriptionStatus = async (userId: string) => {
  const isSubscriptionExist = await prisma.subscription.findFirstOrThrow({
    where: { userId }
  })
  const isActive = isSubscriptionExist.status === "ACTIVE"
    && isSubscriptionExist.currentPeriodEnd
    && new Date(isSubscriptionExist.currentPeriodEnd) > new Date();

  return {
    status: isSubscriptionExist.status,
    isActive,
    currentPeriodEnd: isSubscriptionExist.currentPeriodEnd
  }
}

export const subscriptionService = {
  createCheckoutSession,
  handlewebhook,
  getSubscriptionStatus
};
```
```
┌──────────────┐
│  getSubscriptionStatus(  │
│    userId )                       │
└──────────────┘
              │
              ▼
┌──────────────┐
│  find this user's             │
│  Subscription row               │
└──────────────┘
              │
              ▼
┌──────────────┐        no         ┌──────────────┐
│  status === "ACTIVE"?    │ ────────────────> │  isActive = false     │
└──────────────┘                     └──────────────┘
              │ yes
              ▼
┌──────────────┐        no         ┌──────────────┐
│  currentPeriodEnd is        │ ────────────────> │  isActive = false     │
│  still in the future?         │                     └──────────────┘
└──────────────┘
              │ yes
              ▼
┌──────────────┐
│  isActive = true               │
└──────────────┘
```
**Short explanation:** Both conditions are required, not just the status string. This matters because when a user cancels, Stripe doesn't revoke access instantly — they've already paid for the current period, so `status` alone might still say something ambiguous while a cancellation is pending. Checking the actual date is what correctly keeps access open until the period they already paid for ends.

## `subscription/subscription.utils.ts`

```ts
import Stripe from "stripe";

export const getPeriodEnd = (payload: Stripe.Subscription) => {
  const currentPeriodEndInMilliseconds = payload.items.data[0]?.current_period_end!;
  const currentPeriodEnd = new Date(currentPeriodEndInMilliseconds * 1000);
  return currentPeriodEnd;
};
```
```
┌──────────────┐
│  Stripe subscription       │
│  current_period_end            │
│  (Unix seconds)                   │
└──────────────┘
              │
              ▼   × 1000
┌──────────────┐
│  JS Date object                    │
│  (needs milliseconds)          │
└──────────────┘
```
**Short explanation:** The entire function is one unit conversion. Stripe timestamps are seconds since epoch; JavaScript's `Date` constructor expects milliseconds. Forgetting this `* 1000` is one of the most common Stripe-integration bugs — dates would be wildly wrong (year ~1970-something) instead of erroring loudly, which makes it easy to miss in testing.

```ts
export const handleCheckoutCompleted = async (session: Stripe.Checkout.Session) => {
  const userId = session.metadata?.userId;
  const stripeCustomerId = session.customer as string;
  const stripeSubscriptionId = session.subscription as string;

  if (!userId || !stripeCustomerId || !stripeSubscriptionId) {
    console.log("webhook: missing values for checkout session");
    return;
  }

  const stripeSubscription = await stripe.subscriptions.retrieve(stripeSubscriptionId);
  const currentPeriodEnd = getPeriodEnd(stripeSubscription);

  await prisma.subscription.upsert({
    where: { userId },
    create: { userId, stripeCustomerId, stripeSubscriptionId, status: "ACTIVE", currentPeriodEnd },
    update: { stripeCustomerId, stripeSubscriptionId, status: "ACTIVE", currentPeriodEnd },
  });
};
```
```
┌──────────────┐
│  checkout.session.completed  │
│  event received                    │
└──────────────┘
              │
              ▼
┌──────────────┐        missing      ┌──────────────┐
│  userId / customerId /    │ ─────────────────> │  log + bail out early   │
│  subscriptionId present?     │                       └──────────────┘
└──────────────┘
              │ all present
              ▼
┌──────────────┐
│  fetch full subscription       │
│  details from Stripe              │
└──────────────┘
              │
              ▼
┌──────────────┐        exists      ┌──────────────┐
│  Does a Subscription       │ ─────────────────> │  UPDATE that row            │
│  row for this userId          │                       └──────────────┘
│  already exist?                    │
└──────────────┘        doesn't exist
              │ ──────────────────────────────> ┌──────────────┐
                                                       │  CREATE a new row         │
                                                       └──────────────┘
```
**Short explanation:** This is where a subscription first actually gets written to your database — the checkout redirect (`success_url`) is purely cosmetic for the browser, this webhook handler is what really activates access. `upsert` (update-or-insert) handles both "brand new subscriber" and "resubscribing after a previous cancellation" with one call instead of an if/else.

```ts
export const handleChangeSubscription = async (payload: Stripe.Subscription) => {
  const stripeSubscriptionId = payload.id;
  const status =
    payload.status === "active" || payload.status === "trialing" ? SubscriptionStatus.ACTIVE
    : payload.status === "canceled" ? SubscriptionStatus.CANCELED
    : SubscriptionStatus.EXPIRED;

  const currentPeriodEnd = getPeriodEnd(payload);

  const isSubscriptionExist = await prisma.subscription.findUnique({
    where: { stripeSubscriptionId },
  });

  if (!isSubscriptionExist) {
    console.log(`webhook: no subscription found for id: ${stripeSubscriptionId}`);
    return;
  }

  await prisma.subscription.update({
    where: { stripeSubscriptionId },
    data: { status, currentPeriodEnd },
  });
};
```
```
┌──────────────┐
│  subscription.updated /      │
│  subscription.deleted event      │
└──────────────┘
              │
              ▼
┌──────────────┐
│  translate Stripe's own          │
│  status string → your own          │
│  SubscriptionStatus enum             │
└──────────────┘
              │
              ▼
┌──────────────┐        not found    ┌──────────────┐
│  find the matching        │ ─────────────────> │  log + bail out               │
│  row by stripeSubscriptionId  │                     └──────────────┘
└──────────────┘
              │ found
              ▼
┌──────────────┐
│  UPDATE status +                    │
│  currentPeriodEnd                      │
└──────────────┘
```
**Short explanation:** The status-translation step is deliberate insulation — your database's enum doesn't have to match Stripe's exact vocabulary, so if Stripe adds a new status string later, only this one function needs updating, nothing downstream. **Fixed here:** the original code wrote `currentperiodEnd` (lowercase `p`) while every other function in this file uses `currentPeriodEnd` — that casing mismatch would silently fail to update the field if the real Prisma schema field is `currentPeriodEnd`. Match the casing exactly, everywhere.

## Known Issues Fixed in This Version (vs. the original pasted code)

| Issue | Fix applied above |
|---|---|
| `premium`/`premimum`/`premimu` — three spellings of one module | Standardized to `premium` everywhere |
