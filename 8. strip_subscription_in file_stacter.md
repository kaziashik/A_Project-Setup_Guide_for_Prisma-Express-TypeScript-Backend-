# Reference Notes — Premium Content + Stripe Subscription Module

> Personal reference doc. Explains the pattern behind these two modules (`premium/`, `subscription/`) function-by-function, with flow diagrams, so it's quick to re-implement correctly in a future project.

---

## 0. What This Pattern Actually Does

Two modules working together:
- **`premium/`** — gates access to content (`Post` records where `isPremium: true`) behind login
- **`subscription/`** — handles the actual Stripe billing lifecycle: checkout, payment confirmation via webhook, and tracking whether a user's subscription is currently active

They're separate on purpose: `premium` doesn't know anything about Stripe — it just returns premium posts to whoever's authenticated. Whether that user is *allowed* to see them (i.e. has an active subscription) would be a separate check layered on top, typically inside `premium.service.ts` querying the `Subscription` table, or via a dedicated middleware. **Note:** in the pasted code, `premium.service.ts` does **not** actually check subscription status — it returns all premium posts to any authenticated user regardless of role. That's very likely a gap to close before reusing this, not an intentional design choice (see Section 4).

### 0.1 Naming rule (the one that actually breaks things if skipped)

**Folder name → file prefix → import path → exported variable name must all be the exact same string, every time.** This isn't a style nitpick — the original code this doc is based on had three different spellings for the same module (`premium`, `premimum`, `premimu`) across the folder name and its own imports, which would crash on `Cannot find module` the instant it actually ran. Node doesn't fuzzy-match filenames; a one-letter typo is a different, nonexistent file.

```
folder:  premium/
  premium.router.ts       imports from  "./premium.controller"
  premium.controller.ts   imports from  "./premium.service"
  premium.service.ts      exports       PremiumService

folder:  subscription/
  subscription.route.ts       imports from  "./subscription.controller"
  subscription.controller.ts  imports from  "./subscription.service"
  subscription.service.ts     imports from  "./subscription.utils"
  subscription.utils.ts       exports       getPeriodEnd, handleCheckoutCompleted, handleChangeSubscription
```

Everything below uses these corrected, consistent names — not the typo'd versions from the original snippet.

## 1. The `premium` Module

### 1.1 File-by-file

**`premium.router.ts`** — one route, wraps it in `auth()`:
```ts
router.get("/", auth(Role.ADMIN, Role.AUTHOR, Role.USER), premimController.getPremimuContent)
```
`auth(Role.ADMIN, Role.AUTHOR, Role.USER)` — passing *all three* roles here means "any logged-in user, regardless of role, can hit this route." That's functionally the same as calling `auth()` with no arguments in a system where those are the only three roles that exist — worth simplifying to just `auth()` unless a fourth role could exist later and should be excluded.

**`premium.controller.ts`** — thin HTTP glue, standard shape:
```ts
const getPremimuContent = catchAsync(async (req, res, next) => {
  const result = await PremiumService.getPremiumContent()
  sendResponse(res, { success: true, statusCode: httpStatus.OK, message: "...", data: result })
})
```
Nothing router/response-specific happens beyond calling the service and wrapping the result — this is the same thin-controller pattern used throughout (see your portfolio backend's `experience.controller.js` for the JS/Mongoose equivalent).

**`premium.service.ts`** — the actual query:
```ts
const getPremiumContent = async () => {
  const post = await prisma.post.findMany({ where: { isPremium: true } })
  return post
}
```
Straightforward Prisma query. `catchAsync` is imported here but never used — dead import (see Section 4).

## 2. The `subscription` Module (the complex one)

### 2.1 Files overview

| File | Responsibility |
|---|---|
| `subscription.route.ts` | 3 routes: start checkout, receive Stripe's webhook, check current status |
| `subscription.controller.ts` | HTTP glue for all 3 |
| `subscription.service.ts` | Talks to Stripe + Prisma directly |
| `subscription.utils.ts` | Pure helper functions used by the webhook handler |

### 2.2 `createCheckOutSession` — starting a subscription

```ts
const creatCheckOutSession = async (userId: string) => {
  const transactionResult = await prisma.$transaction(async (tx) => {
    const user = await tx.user.findUniqueOrThrow({ where: { id: userId }, include: { subscription: true } })
    let stripeCustomerId = user.subscription?.stripeCustomerId

    if (!stripeCustomerId) {
      const customer = await stripe.customers.create({ email: user.email, name: user.name, metadata: { userId: user.id } })
      stripeCustomerId = customer.id
    }

    const session = await stripe.checkout.sessions.create({
      line_items: [{ price: config.stripe_product_id, quantity: 1 }],
      mode: "subscription",
      customer: stripeCustomerId,
      payment_method_types: ["card"],
      success_url: `${config.app_url}/premium?success=true`,
      cancel_url: `${config.app_url}/payment?success=false`,
      metadata: { userId: user.id },
    })
    return session.url
  })
  return { paymentUrl: transactionResult }
}
```

**What each part is actually doing:**
- **`prisma.$transaction(...)`** — wraps the read + Stripe calls in a DB transaction. Since nothing here actually writes to the database yet (the write happens later, in the webhook), this transaction wrapper is mostly protecting the *read* consistency of `findUniqueOrThrow` — arguably unnecessary here since no DB write occurs inside it, but harmless.
- **`stripeCustomerId` check** — this is the "returning subscriber vs. new subscriber" branch: if this user already has a Stripe customer ID saved from a previous subscription attempt, reuse it instead of creating a duplicate customer in Stripe's dashboard.
- **`metadata: { userId: user.id }`** — appears **twice**: once on the customer, once on the checkout session. This is the critical link back to your own database — Stripe has no idea what a "userId" is, so you stamp your own ID onto both objects so that later, when a webhook event fires, you can read `event.data.object.metadata.userId` and know which of *your* users it's about.
- **`mode: "subscription"`** — tells Stripe this is a recurring subscription checkout, not a one-time payment.
- **Returns `session.url`** — this is the Stripe-hosted checkout page URL. The frontend redirects the browser here; you never build your own credit-card form.

```
┌──────────────┐   POST /subscription/checkout   ┌──────────────┐

                                                        │  2. create        │

                                                                │

┌──────────────┐   browser redirects to    ┌──────────────┐
│  Frontend       │ ─────────────────────────> │  Stripe-hosted  │

│  = paymentUrl     │                              │  (Stripe's UI,    │
└──────────────┘                              │  not yours)        │
                                                └──────────────┘
                                                        │
                                            user enters card, pays
                                                        │
                    ┌───────────────────────────────────┼───────────────────────────────────┐
                    ▼                                                                         ▼
        ┌──────────────────┐                                                    ┌──────────────────┐
        │  Browser redirected  │                                                    │  Stripe sends a       │
        │  to success_url        │                                                    │  webhook event to      │
        │  (/premium?success=true)│                                                    │  POST /subscription/  │
        └──────────────────┘                                                    │  webhook                │
                                                                                    └──────────────────┘
                                                                                              │
                                                                                              ▼
                                                                                  ┌──────────────────┐
                                                                                  │  handlewebhook()      │
                                                                                  │  actually writes the  │
                                                                                  │  Subscription row       │
                                                                                  └──────────────────┘
```

**The important, easy-to-miss detail here**: the `success_url` redirect and the webhook event are **two separate, independent things** that happen at roughly the same time. The redirect is purely cosmetic — it tells the *browser* where to go. It is **not** what actually activates the subscription in your database. Only the webhook does that. This matters because a user could close their browser tab right after paying, before the redirect finishes — the webhook still fires regardless, so the subscription still gets recorded correctly. **Never** put the "mark subscription active" logic behind the `success_url` route; it has to live in the webhook handler.

### 2.4 `handleWebhok` — verifying and routing Stripe events

```ts
const handleWebhok = catchAsync(async (req, res, next) => {
  const event = req.body as Buffer
  const signature = req.headers['stripe-signature']!
  await subscriptionService.handlewebhook(event, signature as string)
  sendResponse(res, { success: true, statusCode: httpStatus.OK, message: "...", data: {} })
})
```
```ts
const handlewebhook = async (payload: Buffer, signature: string) => {
  const endpointsecret = config.stripe_webhook_secret
  const event = stripe.webhooks.constructEvent(payload, signature, endpointsecret)

  switch (event.type) {
    case "checkout.session.completed": await handleCheckoutCompled(event.data.object); break
    case "customer.subscription.updated": await handleChangeSubscription(event.data.object); break
    case "customer.subscription.deleted": await handleChangeSubscription(event.data.object); break
    default: break
  }
}
```

**Why `req.body as Buffer` matters — this is the #1 thing people get wrong with Stripe webhooks:**
`stripe.webhooks.constructEvent()` needs the **raw, untouched request body bytes** to verify the signature cryptographically. If your Express app has already run `express.json()` on this route (which parses the body into a JS object), the raw bytes are gone and signature verification will **always fail**. The route handling `/webhook` must be configured with `express.raw({ type: "application/json" })` instead of the normal JSON body parser — and it has to be registered **before** any global `express.json()` middleware, or scoped specifically to bypass it for this one route.

```
┌───────────────────────┐
│  Stripe sends webhook     │
│  with raw JSON body +      │
│  Stripe-Signature header    │
└───────────────────────┘
              │
              ▼
┌───────────────────────┐        wrong        ┌──────────────────────┐
│  If express.json() ran   │ ───────────────────> │  Signature verify FAILS │
│  first (body is now an    │                       │  — Stripe retries        │
│  object, not raw bytes)    │                       │  forever, never succeeds  │
└───────────────────────┘                       └──────────────────────┘
              │
          (must avoid this)
              ▼
┌───────────────────────┐       correct        ┌──────────────────────┐
│  express.raw() used on    │ ───────────────────> │  Signature verify OK    │
│  this route only, body      │                       │  event processed          │
│  stays raw Buffer            │                       │  normally                    │
└───────────────────────┘                       └──────────────────────┘
```

**The `switch` on `event.type`** — Stripe sends dozens of event types; you only care about three here:
- `checkout.session.completed` — fires once, right after a successful first payment
- `customer.subscription.updated` — fires on *any* change to the subscription object (plan change, renewal, trial-to-active transition, and also when it's canceled but not yet deleted)
- `customer.subscription.deleted` — fires when the subscription is actually removed (e.g. after a cancellation's grace period ends)

### 2.5 `subscription.utils.ts` — the actual database writes

**`getPeriodEnd`** — Stripe gives you a Unix timestamp (seconds since epoch); JS `Date` expects milliseconds:
```ts
const currentPeriodEnd = new Date(currentPeriodEndInMilliseconds * 1000)
```
Multiplying by `1000` is the whole function — a very common one-line gotcha whenever you handle any Stripe timestamp.

**`handleCheckoutCompled`** — this is where a subscription first gets written to your database:
```ts
await prisma.subscription.upsert({
  where: { userId },
  create: { userId, stripeCustomerId, stripeSubscriptionId, status: "ACTIVE", currentPeriodEnd },
  update: { stripeCustomerId, stripeSubscriptionId, status: "ACTIVE", currentPeriodEnd },
})
```
`upsert` (update-or-insert) is the right call here — a user's very first subscription needs `create`, but if they previously subscribed, canceled, and are now resubscribing, the same `userId` row already exists and needs `update` instead. One line handles both cases instead of an if/else.

**`handleChangeSubscription`** — maps Stripe's own status strings to your own `SubscriptionStatus` enum:
```ts
const status =
  payload.status === "active" || payload.status === "trialing" ? SubscriptionStatus.ACTIVE
  : payload.status === "canceled" ? SubscriptionStatus.CANCELED
  : SubscriptionStatus.EXPIRED
```
This is a deliberate translation layer — your database's `SubscriptionStatus` enum doesn't have to match Stripe's exact status vocabulary one-to-one, and shouldn't: it insulates the rest of your app from Stripe's specific terminology, so if Stripe adds a new status string later, only this one function needs updating.

### 2.6 `getSubscriptionStatus` — how "is this user allowed in" actually gets decided

```ts
const isActive = isSubscriptionExist.status === "ACTIVE"
  && isSubscriptionExist.currentPeriodEnd
  && new Date(isSubscriptionExist.currentPeriodEnd) > new Date()
```
**Two conditions, both required:**
1. The stored `status` says `"ACTIVE"`
2. **And** today's date is still before `currentPeriodEnd`

The second check matters because of a subtle timing gap: if a user cancels, Stripe doesn't revoke access instantly — they've already paid for the current billing period, so `status` might still say something reflecting "active until period end" while a cancellation is pending. Checking the actual date, not just the status string, is what correctly keeps access open until the period they already paid for actually ends.

## 3. Shared Patterns Tying Both Modules Together

- **`auth(...roles)`** — same role-gate pattern in both modules' routers. Compare to your own portfolio backend's simplified `auth()` with no roles — the difference is purely because that project has exactly one admin, while this one has multiple user roles to distinguish.
- **`catchAsync`** — identical purpose to the one you already use: wraps the async controller so a thrown/rejected error goes to `next(error)` instead of crashing the process.
- **`sendResponse`** — same consistent-response-shape idea, just with `httpStatus` (a small npm package of named HTTP status constants) instead of hardcoded numbers.

## 4. Bugs / Inconsistencies Spotted in This Code (fix before reusing)

| Issue | Where | Fix |
|---|---|---|
| Folder/file/import naming mismatch — three spellings of the same module: `premium`, `premimum`, `premimu` | `premium.router.ts` imports `"./premimum.controller"`, `premium.controller.ts` imports `"./premimu.service"` | Pick one spelling (`premium`) and use it identically in the folder name, every filename, every import path, and every exported variable — see Section 0.1 |
| Same issue in the other module: `subscription.utils.ts` (file) vs. `"./subscription.utilits"` (import) | `subscription.service.ts` | Fix the import to `"./subscription.utils"` to match the actual filename |
| Unused import `catchAsync` | `premium.service.ts` | Remove — services shouldn't need `catchAsync` at all, that belongs at the controller layer only |
| Unused import `strict` from `"assert"` | `subscription.service.ts` | Remove |
| Field name casing mismatch: fetched as `currentPeriodEnd` but written back as `currentperiodEnd` (lowercase `p`) | `handleChangeSubscription` in `subscription.utils.ts` | This likely **silently fails to update the field** if Prisma's schema field is actually `currentPeriodEnd` — align casing exactly, or Prisma will either error or (depending on your Prisma version's strictness) silently ignore the unknown key |
| `getSubscriptionStatus` returns `{ result }` (nested) while its own type/shape elsewhere expects the fields directly | `subscription.controller.ts` | Decide once whether responses nest data under a named key or spread it flat, and stay consistent — mixing both across endpoints makes frontend consumption inconsistent |
| `premium` route grants access to **any** authenticated user, without checking subscription status at all | `premium.service.ts` | If premium content is meant to require an *active paid subscription* (not just being logged in), add a check here — e.g. query `Subscription` for that `userId` and confirm `status === "ACTIVE"` and `currentPeriodEnd > now`, reusing the exact logic from `getSubscriptionStatus` |

## 5. Checklist — Implementing This Pattern Fresh in a New Project

- [ ] Add `stripe` npm package, get API keys (test mode first) from the Stripe dashboard
- [ ] Create a Stripe Product + Price in the dashboard, save the Price ID to config
- [ ] Set up a webhook endpoint in the Stripe dashboard pointing at `<your-domain>/subscription/webhook`, copy the signing secret into config
- [ ] **Critical**: configure the webhook route with `express.raw({ type: "application/json" })`, registered before (or excluded from) any global `express.json()` middleware
- [ ] Build `createCheckoutSession`: find-or-create Stripe customer → create checkout session with `metadata.userId` set → return `session.url`
- [ ] Build the webhook handler: verify signature → switch on `event.type` → handle at minimum `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`
- [ ] Build `getSubscriptionStatus`: check both `status === "ACTIVE"` **and** `currentPeriodEnd > now`
- [ ] Test locally with the Stripe CLI (`stripe listen --forward-to localhost:PORT/subscription/webhook`) before deploying — this forwards real webhook events to your local server during development
- [ ] Gate any "premium" content behind the same active-subscription check, not just "is logged in"
