# Centralized Error Handling — AppError + globalErrorHandler

Why every backend project should have this from day one, how the pieces fit together, and how to retrofit it into a project that's already using plain `throw new Error(...)` everywhere.

---

## 1. Core Concepts (read this before the code)

### Why a custom `AppError` class instead of just `throw new Error(message)`
A plain `Error` only carries a message — nothing tells your API layer *what HTTP status code* to respond with. Without a way to attach that, your global error handler has no choice but to guess, and usually defaults everything to `500 Internal Server Error` — even for things that are clearly the client's fault, like "email already exists" (should be `409`) or "invalid credentials" (should be `401`). `AppError extends Error` and adds exactly one thing on top: a `statusCode` that travels with the error all the way to the response.

### Why `AppError` still extends `Error`, rather than being a totally separate class
Node's error handling (try/catch, `instanceof Error` checks used by many libraries, stack traces) is built around the `Error` class. By extending it, `AppError` gets all of that behavior for free — `.message`, `.stack`, and compatibility with anything that expects a real `Error` — while adding your own `statusCode` field on top.

### Why `Error.captureStackTrace(this, this.constructor)` matters
Without this line, the stack trace attached to an `AppError` would start from *inside* the `AppError` constructor itself — showing you `AppError.ts` as the top of the stack, which is useless for debugging. `captureStackTrace` tells V8 (Node's JS engine) to omit the constructor's own frames and start the trace from wherever `throw new AppError(...)` was actually called — the file and line you actually care about when debugging.

### Why the `stack` parameter is optional with an `if/else`
This lets `AppError` do the right thing in two different situations: normally, you just throw a fresh error and want a fresh, accurate stack trace (the `else` branch). But occasionally you might be *re-throwing* an error that already has a stack trace you want to preserve (e.g., wrapping a caught error from somewhere else) — the optional `stack` parameter lets you pass that through instead of generating a new one.

### Why one central `globalErrorHandler` instead of handling errors in every controller
Without this, every single controller needs its own try/catch and its own `res.status(...).json(...)` formatting — easy to get inconsistent (one endpoint returns `{ error: "..." }`, another returns `{ message: "..." }`). A global error handler, combined with `catchAsync` forwarding every thrown error to `next(err)`, means **every single endpoint in your app returns errors in exactly the same shape**, without repeating that logic anywhere.

### Why Prisma errors get special-cased before the generic `Error` check
Prisma throws its own specific error classes (`PrismaClientValidationError`, `PrismaClientKnownRequestError`, etc.) with their own error codes (`P2002` = unique constraint violation, `P2003` = foreign key failure, `P2025` = record not found). These aren't `AppError`s — they come straight from the database layer — but they're still things you want to turn into clean, specific HTTP responses (`400 Bad Request` for "duplicate key", not a raw Prisma stack trace leaking to the client). The `instanceof` checks translate Prisma's internal error codes into your API's actual language.

### Why the order of the `if/else if` chain matters
`instanceof` checks need to go from *most specific* to *most generic*. `AppError` and every `PrismaClientXError` type are checked first; the plain `err instanceof Error` check comes last, as a catch-all for anything that doesn't match a more specific type above it. If you reversed the order (checked `Error` first), every Prisma error and every `AppError` would incorrectly get caught by the generic branch, since they're all `Error` subclasses too — and you'd lose all the specific handling above.

### Why `config.node_env === "development"` gates what gets sent back
In development, you want the *real* error message, name, and stack trace visible — that's what makes debugging fast. In production, leaking stack traces and internal error details to a client (or worse, an attacker) is a real security risk — it can reveal file paths, library versions, or database structure. This is why every field that could leak internals falls back to a generic `"Internal Server Error"` string once `NODE_ENV` isn't `"development"`.

## 2. `AppError.ts`

```typescript
export class AppError extends Error {

    public statusCode : number

    constructor(statusCode : number , message : string, stack = "") {
        super(message) // throw new Error(message)

        this.statusCode = statusCode

        if(stack){
            this.stack = stack
        }else{
            Error.captureStackTrace(this, this.constructor)
        }
    }
}

//throw new AppError(404, "Not Found")
```

**Usage anywhere in your app:**

```typescript
if (!user.isVerified) {
  throw new AppError(httpStatus.FORBIDDEN, "Email not verified");
}

if (user.status === UserStatus.BANNED) {
  throw new AppError(httpStatus.FORBIDDEN, "User is blocked");
}
```

## 3. `globalErrorHandler.ts`

```typescript
import type { NextFunction, Request, Response } from "express";
import httpStatus from "http-status";
import { Prisma } from "../../generated/prisma/client";
import config from "../config";
import { AppError } from "../utils/AppError";

export const globalErrorHandler = async (
	err: any,
	_req: Request,
	res: Response,
	_next: NextFunction,
) => {
	if (config.node_env === "development") {
		console.log("Error from Global Error Handler", err);
	}

	let statusCode: number = httpStatus.INTERNAL_SERVER_ERROR;
	let errorMessage = err.message || "Internal Server Error";
	const errorName = err.name || "Internal Server Error";
	// let errorDetails = err.stack

	if (err instanceof Prisma.PrismaClientValidationError) {
		statusCode = httpStatus.BAD_REQUEST;
		errorMessage = "You have provided incorrect field type or missing fields";
	} else if (err instanceof Prisma.PrismaClientKnownRequestError) {
		if (err.code === "P2002") {
			(statusCode = httpStatus.BAD_REQUEST),
				(errorMessage = "Duplicate Key Error");
		} else if (err.code === "P2003") {
			(statusCode = httpStatus.BAD_REQUEST),
				(errorMessage = "Foreign key constraint failed");
		} else if (err.code === "P2025") {
			(statusCode = httpStatus.BAD_REQUEST),
				(errorMessage =
					"An operation failed because it depends on one or more records that were required but not found.");
		}
	} else if (err instanceof Prisma.PrismaClientInitializationError) {
		if (err.errorCode === "P1000") {
			statusCode = httpStatus.UNAUTHORIZED;
			errorMessage =
				"Authentication failed against database server. Please Check Your Credentials";
		} else if (err.errorCode === "P1001") {
			statusCode = httpStatus.BAD_REQUEST;
			errorMessage = "Can't reach database server";
		}
	} else if (err instanceof Prisma.PrismaClientUnknownRequestError) {
		statusCode = httpStatus.INTERNAL_SERVER_ERROR;
		errorMessage = "Error occurred during query execution";
	} else if( err instanceof AppError){
		errorMessage = err.message
		statusCode = err.statusCode

	} else if (err instanceof Error) {
		errorMessage = err.message;
	}

	res.status(statusCode).json({
		success: false,
		statusCode: statusCode || httpStatus.INTERNAL_SERVER_ERROR,
		name:
			config.node_env === "development" ? errorName : "Internal Server Error",
		message:
			config.node_env === "development"
				? errorMessage
				: "Internal Server Error",
		error: config.node_env === "development" ? err : undefined,
		stack: config.node_env === "development" ? err.stack : undefined,
	});
};
```

**Wiring it in — this must be the *last* `app.use(...)` in `app.ts`**, after every route:

```typescript
import { globalErrorHandler } from "./app/middleware/globalErrorHandler";

// ...all your routes go above this line

app.use(globalErrorHandler);
```

Express recognizes an error-handling middleware specifically by its four-parameter signature (`err, req, res, next`) — and it only ever gets called when something upstream calls `next(err)` or throws inside an async handler wrapped by `catchAsync`.

## 4. Set this up *before* writing any feature code

The reason this is worth doing on day one, not retrofitted later: once you have `AppError` + `globalErrorHandler` wired up, every feature you build afterward gets consistent, correctly-coded error responses **for free** — you just `throw new AppError(...)` wherever a business rule fails, and the response shape, status code, and dev/prod detail-hiding are already solved. Building features first and adding this later means going back through every `throw new Error(...)` you already wrote and manually upgrading each one.

## 5. Retrofitting an existing project (if you already have plain `Error` throws everywhere)

If a project already has scattered `throw new Error("some message")` calls and you want to convert them to `AppError` with proper status codes, doing this by hand file-by-file is slow and easy to get inconsistent (picking the wrong status code, missing some call sites entirely). This is a good use case for an AI coding agent that can read your whole codebase and make the same kind of judgment call consistently everywhere — tools like **Claude Code** (terminal or VS Code) or **opencode** are built for exactly this kind of project-wide, context-aware refactor.

### Setting up Claude Code in VS Code
1. Install the **Claude Code** extension from the VS Code marketplace (or run `npm install -g @anthropic-ai/claude-code` for the terminal version, if you prefer working from the command line alongside your editor)
2. Open your project folder in VS Code
3. Open the Claude Code panel/terminal from within the editor — it has access to read your project's files directly, not just what you paste into a chat window

### A reasonable prompt for this specific retrofit
```
Go through this Express + TypeScript project and find every place that does
`throw new Error("...")`. Replace each one with `throw new AppError(statusCode, "...")`,
using the AppError class already defined in src/app/utils/AppError.ts.

Pick the correct HTTP status code based on what the error actually represents:
- "not found" type errors → 404
- "already exists" / duplicate → 409
- validation failures / bad input → 400
- authentication failures (wrong password, invalid token) → 401
- authorization failures (wrong role, banned, forbidden) → 403
- anything else → 500

Import AppError and httpStatus in every file you modify. Show me a summary
of every file changed and the status code you chose for each error, so I can
review before committing.
```

### Why "show me a summary before committing" matters
An AI agent making a judgment call on 40+ error messages across a project will get most of them right, but status-code choice is genuinely ambiguous sometimes (is "user not verified" a `403` or a `401`? Reasonable people disagree). Reviewing a summary of every change — rather than blindly accepting a mass rewrite — is the same discipline as reviewing any other pull request, just compressed into one pass instead of scrolling through every file yourself.

### After the agent runs
1. Run `npx tsc --noEmit` to confirm every file still compiles (a missed import, wrong argument order, etc. would show up here immediately)
2. Spot-check a handful of the status code choices against your own judgment
3. Test a few endpoints manually to confirm the actual HTTP response codes match what you expect

## 6. Worth knowing about the code above (not rewritten, just flagged)

- **`err.name` for an `AppError` instance will just say `"Error"`**, not `"AppError"` — since `AppError`'s constructor never overrides `this.name`. If you want the `name` field in your error responses to actually say `"AppError"`, add `this.name = "AppError";` inside the constructor. Not required for the handler to work correctly, just affects what shows up in that one field during development.
- **`statusCode: statusCode || httpStatus.INTERNAL_SERVER_ERROR`** — this fallback is redundant, since `statusCode` is already initialized to `httpStatus.INTERNAL_SERVER_ERROR` at the top of the function and only ever gets reassigned to a real number in each branch. Harmless as-is, just not doing anything.
