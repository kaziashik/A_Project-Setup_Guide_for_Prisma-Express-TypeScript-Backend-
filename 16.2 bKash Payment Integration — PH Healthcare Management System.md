# bKash Payment Integration — PH Healthcare Management System

How an appointment gets paid for via bKash, how that data lands in the database, and how cancellation + refund works.

---

## 1. Core Concepts (read this before the code)

### Why payment is tied to a `Payment` row, not just a status flag on `Apppointment`
An appointment's payment has its own lifecycle — pending, paid, failed, cancelled, refunded — plus a growing pile of gateway-specific data (transaction IDs, raw API responses, refund details). Cramming all of that onto the `Apppointment` model itself would make it bloated and would mix two different concerns (scheduling vs. money) into one table. Splitting them into two models, linked 1:1, keeps each one focused.

### Why `Payment.appointmentId` is `@unique`
This enforces the 1:1 relationship at the database level: exactly one payment record per appointment. Combined with `appointment Payment?` (optional) on the `Apppointment` side, this means an appointment can exist with *no* payment yet (right after booking, before checkout), then gets exactly one `Payment` row once payment is initiated.

### The three-step bKash flow
1. **Create** (`/tokenized/checkout/create`) — your server tells bKash "a patient wants to pay this amount for this appointment." bKash responds with a `paymentID` and a `bkashURL` — a hosted checkout page you redirect the patient to.
2. **Patient pays** on bKash's own page — your server isn't involved in this part at all; it's happening entirely on bKash's domain.
3. **Execute** (`/tokenized/checkout/execute`) — after the patient finishes (or cancels/fails), bKash redirects their browser back to *your* callback URL with a `paymentID` and a `status` query param. Your server then calls `execute` to confirm what actually happened and pull the final transaction details.

**Why "execute" is a separate step, not just trusting the redirect's query params:** the `status` value on the redirect URL isn't cryptographically verified — someone could hand-edit the URL to say `status=success` without ever actually paying. Calling `execute` is your server directly asking bKash's API "what really happened with this `paymentID`," which is the only source of truth you should trust before marking anything as paid.

### Why `merchantInvoiceNumber` is the `Apppointment.id`
bKash needs some way to tell your callback which of *your* records this payment belongs to. Reusing your own `Apppointment.id` as the invoice number means the callback handler can go straight from `executedPaymentResult.merchantInvoiceNumber` back to `apppointment.update({ where: { id: ... } })` with no extra lookup table needed.

### Why everything runs inside `prisma.$transaction`
Creating the appointment/payment row and calling bKash's API are operations that need to succeed or fail *together*. If the bKash API call throws after a database write already committed, you'd be left with a row referencing a transaction that never actually happened. Wrapping the whole sequence in `$transaction` means any thrown error rolls back every database write inside that block, so your data never ends up half-committed.

**What's actually inside the `bookAppointment` transaction, in order:**

```
┌─ prisma transaction rollback ─────────────────────────────────────────┐
│                                                                        │
│   ┌─────────────────┐   ┌──────────────────┐   ┌────────────────────┐│
│   │   appointment    │   │   bkash payment   │   │  payment model     ││
│   │      create       │   │      create        │   │       create       ││
│   └─────────────────┘   └──────────────────┘   └────────────────────┘│
│         prisma                  bkash                   prisma        │
│                                                                        │
└────────────────────────────────────────────────────────────────────┘
```

Three steps, two of them talking to your own database (Prisma) and one talking out to bKash's servers, all inside one `tx` block:

1. **`appointment` create (prisma)** — `tx.apppointment.create(...)`. A real row exists, `status: PENDING`, before anything else happens.
2. **`bkash payment` create (bkash)** — the `fetch(...)` call to bKash's `/tokenized/checkout/create`. This is the one step that leaves your own system — if it throws or bKash rejects it, everything rolls back, so you never end up with an `Apppointment` row that has no corresponding payment attempt.
3. **`payment model` create (prisma)** — `tx.payment.create(...)`, storing bKash's response (`paymentID`, `bkashURL`, etc.) against that same appointment.

**Why the order matters:** the appointment has to exist *before* you can call bKash (step 2 needs `appointment.id` for `merchantInvoiceNumber`), and the `Payment` row has to be created *after* bKash responds (step 3 needs `bkashCreatePaymentResult` to actually have something to store). If step 2 or step 3 throws, Prisma rolls back step 1 too — so a failed bKash call never leaves an orphaned, payment-less appointment sitting in your database.

**What's inside the `bookAppointmentCallback` transaction:**

```
┌─ prisma transaction rollback ─────────────────────────────────────────┐
│                                                                        │
│   ┌──────────────────┐   ┌──────────────────┐   ┌───────────────────┐│
│   │   bkash payment    │   │   appointment      │   │   payment          ││
│   │      execute        │   │      update          │   │      update          ││
│   └──────────────────┘   └──────────────────┘   └───────────────────┘│
│         bkash                   prisma                  prisma        │
│                                                                        │
└────────────────────────────────────────────────────────────────────┘
```

1. **`bkash payment` execute (bkash)** — confirms with bKash's server what actually happened to this `paymentID`. This is the trusted source of truth, not the raw `status` query param on the redirect URL.
2. **`appointment` update (prisma)** — flips `Apppointment.status` to `CONFIRMED` (only on the success branch).
3. **`payment` update (prisma)** — writes the real `bkashTrxId`, `paidAt`, and the full `gatewayResponse` onto the existing `Payment` row.

If step 2 or 3 throws (e.g. a database error), the transaction rolls back — meaning you never end up in a state where bKash thinks the payment succeeded but your own `Apppointment`/`Payment` rows never reflect it. Worth noting: bKash itself already processed the money by this point regardless of whether your database write succeeds — the rollback protects your *data consistency*, not the money movement itself. That's why this callback endpoint should be safe to call more than once with the same result (idempotent) — if your database write fails and bKash retries the callback, running `execute` again and re-applying the same update shouldn't cause harm.

**What's inside the `cancelAppointment` transaction:**

```
┌─ prisma transaction rollback ─────────────────────────────────────────┐
│                                                                        │
│  ┌───────────────┐  ┌───────────────┐  ┌───────────────┐  ┌─────────┐│
│  │  appointment    │  │  appointment    │  │  bkash refund   │  │ payment  ││
│  │    find (+pay)   │  │     update        │  │      create       │  │  update  ││
│  └───────────────┘  └───────────────┘  └───────────────┘  └─────────┘│
│        prisma              prisma               bkash          prisma  │
│                                                                        │
└────────────────────────────────────────────────────────────────────┘
```

1. **`appointment` find (prisma)** — pulls the appointment *with* its related `Payment` row (`include: { payment: true }`), since the refund step needs `bkashPaymentId`/`bkashTrxId`/`amount` off that payment.
2. **`appointment` update (prisma)** — flips `Apppointment.status` to `CANCELLED`. This happens *before* the refund call, not after — worth noting as a deliberate choice: the appointment is considered cancelled the moment the patient requests it, independent of whether the refund itself succeeds a moment later.
3. **`bkash refund` create (bkash)** — calls bKash's `/tokenized/checkout/payment/refund` endpoint using the stored payment details.
4. **`payment` update (prisma)** — records the refund result (`refundTrxId`, `refundAmount`, `refundedAt`) and flips `Payment.status` to `REFUNDED`.

Same rollback logic applies: if the refund API call (step 3) throws, steps 1–2 roll back too — so an appointment never ends up marked `CANCELLED` in your database while the refund silently never happened.

### Why cancellation checks appointment status before attempting a refund
You shouldn't refund an appointment that was never paid, and you generally shouldn't let someone cancel one that's already `ONGOING` or `COMPLETED`. The cancel flow checks status first, and only calls bKash's refund endpoint if a `Payment` record actually exists for that appointment.

### `bookAppointment` vs `payAppointment` — two different entry points
`bookAppointment` creates a brand-new `Apppointment` *and* immediately starts the bKash payment flow for it, all in one transaction — this is the normal "book and pay right away" path. `payAppointment` is a retry path: it assumes an appointment already exists (still `PENDING`) and re-initiates payment against it — useful if a patient abandoned the bKash checkout page the first time and wants to try again without creating a duplicate appointment.

## 2. Schema

```prisma
model Payment {
  id String @id @default(uuid())

  status PaymentStatus @default(UNPAID)

  amount   Decimal @db.Decimal(10, 2) // 100.50
  currency String  @default("BDT")

  paymentGateway        String @default("bkash")
  merchantInvoiceNumber String @unique // appointment id

  bkashPaymentId String? @unique
  bkashTrxId     String?
  payerReference String? // user email / phone number
  paidAt         String?

  gatewayResponse Json?

  refundTrxId  String?
  refundAmount Decimal? @db.Decimal(10, 2)
  refundReason String?
  refundedAt   String?

  appointmentId String       @unique
  appointment   Apppointment @relation(fields: [appointmentId], references: [id], onDelete: Cascade, onUpdate: Cascade)

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@map("payments")
}
```

```prisma
model Apppointment {
  id String @id @default(uuid())

  status AppointmentStatus @default(PENDING)

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  payment Payment?

  @@map("appointments")
}
```

## 5. Service

```typescript
import {
	AppointmentStatus,
	PaymentStatus,
} from "../../../generated/prisma/enums";
import config from "../../config";
import { getBkashIdToken } from "../../lib/bkash";
import { prisma } from "../../lib/prisma";
import type { RequestUser } from "../../middleware/checkAuth";

const bookAppointment = async (payload: any, user: RequestUser) => {
	const transactionResult = await prisma.$transaction(async (tx) => {
		// business logic

		const appointment = await tx.apppointment.create({
			data: {
				status: AppointmentStatus.PENDING,
			},
		});

		const bkashIdToken = await getBkashIdToken();

		if (!bkashIdToken) {
			throw new Error("No Bkash Access Token Found!");
		}

		const bkashCreatePaymentResponse = await fetch(
			`${config.bkash_base_url}/tokenized/checkout/create`,
			{
				method: "POST",
				headers: {
					"Content-Type": "application/json",
					Accept: "application/json",
					Authorization: bkashIdToken,
					"X-App-Key": config.bkash_app_key,
				},
				body: JSON.stringify({
					mode: "0011",
					// payerReference: "0123456789", //user email or phone number
					payerReference: user.email, //user email or phone number
					callbackURL: `${config.bkash_callback_url}/appointment/book-appointment/payment/callback`,
					amount: "1200",
					currency: "BDT",
					intent: "sale",
					// merchantInvoiceNumber: "Inv4" // apppointment id
					merchantInvoiceNumber: appointment.id, // apppointment id
				}),
			},
		);

		const bkashCreatePaymentResult = await bkashCreatePaymentResponse.json();

		//paymen model create

		await tx.payment.create({
			data: {
				merchantInvoiceNumber: bkashCreatePaymentResult.merchantInvoiceNumber,
				appointmentId: appointment.id,
				amount: "1200",
				gatewayResponse: bkashCreatePaymentResult,
				bkashPaymentId: bkashCreatePaymentResult.paymentID,
				payerReference: user.email,
			},
		});

		return {
			paymentUrl: bkashCreatePaymentResult.bkashURL,
		};
	});

	return transactionResult;
};

const payAppointment = async (payload: any, user: RequestUser) => {
	const appointmentId = payload.appointmentId;

	const existingAppointment = await prisma.apppointment.findUnique({
		where: {
			id: appointmentId,
		},
	});

	if (!existingAppointment) {
		throw new Error("Appointment Does Not Exists");
	}

	if (existingAppointment.status !== "PENDING") {
		throw new Error("Appointment Is Not Pending!");
	}

	// if (existingAppointment.status === "CANCELLED" || existingAppointment.status === "ONGOING" || existingAppointment.status === "COMPLETED"){
	//     const appointmentStatus = existingAppointment.status
	//     throw new Error(`Appointment is already ${appointmentStatus.toLowerCase}`)
	// }

	const bkashIdToken = await getBkashIdToken();

	if (!bkashIdToken) {
		throw new Error("No Bkash Access Token Found!");
	}

	const bkashCreatePaymentResponse = await fetch(
		`${config.bkash_base_url}/tokenized/checkout/create`,
		{
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				Accept: "application/json",
				Authorization: bkashIdToken,
				"X-App-Key": config.bkash_app_key,
			},
			body: JSON.stringify({
				mode: "0011",
				// payerReference: "0123456789", //user email or phone number
				payerReference: user.email, //user email or phone number
				callbackURL: `${config.bkash_callback_url}/appointment/book-appointment/payment/callback`,
				amount: "1200",
				currency: "BDT",
				intent: "sale",
				// merchantInvoiceNumber: "Inv4" // apppointment id
				merchantInvoiceNumber: existingAppointment.id, // apppointment id
			}),
		},
	);

	const bkashCreatePaymentResult = await bkashCreatePaymentResponse.json();

	await prisma.payment.update({
		where: {
			appointmentId: existingAppointment.id,
		},

		data: {
			merchantInvoiceNumber: bkashCreatePaymentResult.merchantInvoiceNumber,
			gatewayResponse: bkashCreatePaymentResult,
			bkashPaymentId: bkashCreatePaymentResult.paymentID,
		},
	});

	return {
		paymentUrl: bkashCreatePaymentResult.bkashURL,
	};
};

const bookAppointmentCallback = async (query: Record<string, any>) => {
	const transactionResult = await prisma.$transaction(async (tx) => {
		const paymentId = query.paymentID;

		if (!paymentId) {
			throw new Error("Payment Id Missing");
		}

		const status = query.status;

		if (!status) {
			throw new Error("Payment Status is Missing");
		}

		const bkashIdToken = await getBkashIdToken();

		if (!bkashIdToken) {
			throw new Error("No Bkash Access Token Found!");
		}

		const executedPaymentResponse = await fetch(
			`${config.bkash_base_url}/tokenized/checkout/execute`,
			{
				method: "POST",
				headers: {
					"Content-Type": "application/json",
					Accept: "application/json",
					Authorization: bkashIdToken,
					"X-App-Key": config.bkash_app_key,
				},

				body: JSON.stringify({
					paymentID: paymentId,
				}),
			},
		);

		const executedPaymentResult = await executedPaymentResponse.json();

		if (status === "success") {
			await tx.apppointment.update({
				where: {
					id: executedPaymentResult.merchantInvoiceNumber,
				},
				data: {
					status: AppointmentStatus.CONFIRMED,
				},
			});

			await tx.payment.update({
				where: {
					appointmentId: executedPaymentResult.merchantInvoiceNumber,
					bkashPaymentId: paymentId,
				},
				data: {
					status: PaymentStatus.PAID,
					bkashTrxId: executedPaymentResult.trxID,
					paidAt: executedPaymentResult.paymentExecuteTime,
					gatewayResponse: executedPaymentResult,
				},
			});

			return {
				redirectUrl: `${config.frontend_url}/dashboard/my-appointments?status=success`,
			};
		} else if (status === "failure") {
			await tx.payment.update({
				where: {
					bkashPaymentId: paymentId,
				},
				data: {
					status: PaymentStatus.FAILED,
					gatewayResponse: executedPaymentResult,
				},
			});
			return {
				redirectUrl: `${config.frontend_url}/dashboard/my-appointments?status=failue`,
			};
		} else if (status === "cancel") {
			await tx.payment.update({
				where: {
					bkashPaymentId: paymentId,
				},
				data: {
					status: PaymentStatus.CANCELLED,
					gatewayResponse: executedPaymentResult,
				},
			});
			return {
				executedPaymentResult,
				redirectUrl: `${config.frontend_url}/dashboard/my-appointments?status=cancel`,
			};
		} else {
			return {
				executedPaymentResult,
				redirectUrl: `${config.frontend_url}/dashboard/my-appointments?error=payment-failed`,
			};
		}
	});

	return transactionResult;
};

const cancelAppointment = async (payload: any) => {
	const transactionResult = await prisma.$transaction(async (tx) => {
		const appointmentId = payload.appointmentId;

		const existingAppointment = await tx.apppointment.findUnique({
			where: {
				id: appointmentId,
			},
			include: {
				payment: true,
			},
		});

		if (!existingAppointment) {
			throw new Error("Appointment Does Not Exists");
		}

		if (
			existingAppointment.status === "ONGOING" ||
			existingAppointment.status === "COMPLETED"
		) {
			throw new Error("Appointment Ongoing or Completed");
		}

		if (existingAppointment.status === "CANCELLED") {
			throw new Error("Appointment Already Cancelled");
		}

		const updatedAppointment = await tx.apppointment.update({
			where: {
				id: existingAppointment.id,
			},
			data: {
				status: "CANCELLED",
			},
		});

		const bkashIdToken = await getBkashIdToken();

		if (!bkashIdToken) {
			throw new Error("No Bkash Access Token Found!");
		}

		const bkashRefundPaymentResponse = await fetch(
			`${config.bkash_base_url}/tokenized/checkout/payment/refund`,
			{
				method: "POST",
				headers: {
					"Content-Type": "application/json",
					Accept: "application/json",
					Authorization: bkashIdToken,
					"X-App-Key": config.bkash_app_key,
				},
				body: JSON.stringify({
					paymentID: existingAppointment.payment?.bkashPaymentId,
					trxID: existingAppointment.payment?.bkashTrxId,
					amount: existingAppointment.payment?.amount.toString(),
					sku: "Appointment Cancellation",
					reason: "Patient Cancelled The Appointment",
				}),
			},
		);

		const bkashRefundPaymentResult = await bkashRefundPaymentResponse.json();

		const updatedPayment = await tx.payment.update({
			where: {
				appointmentId: existingAppointment.id,
			},
			data: {
				refundTrxId: bkashRefundPaymentResult.refundTrxID,
				refundedAt: bkashRefundPaymentResult.completedTime,
				refundAmount: bkashRefundPaymentResult.amount,
				refundReason: "Patient Cancelled The Appointment",
				status: PaymentStatus.REFUNDED,
				gatewayResponse: bkashRefundPaymentResult,
			},
		});

		return {
			appointment: updatedAppointment,
			payment: updatedPayment,
		};
	});

	return transactionResult;
};

export const AppointmentServices = {
	bookAppointment,
	payAppointment,
	bookAppointmentCallback,
	cancelAppointment,
};
```

## 6. The overall flow, end to end

1. Patient hits `POST /book-appointment` → `Apppointment` created (`PENDING`) + bKash `create` called + `Payment` row created → patient gets redirected to `bkashURL`
2. Patient pays on bKash's hosted page
3. bKash redirects the browser to `GET /book-appointment/payment/callback?paymentID=...&status=...`
4. Backend calls bKash `execute` to confirm the real result, then updates `Apppointment.status` → `CONFIRMED` and `Payment.status` → `PAID` (or `FAILED`/`CANCELLED` depending on outcome)
5. If the patient abandoned checkout the first time and the appointment is still `PENDING`, `POST /pay-appointment` re-initiates a fresh bKash `create` against the same appointment
6. `POST /cancel-appointment` — blocked if `ONGOING`/`COMPLETED`/already `CANCELLED`; otherwise marks the appointment `CANCELLED` and, if a `PAID` payment exists, calls bKash's refund endpoint and updates `Payment.status` → `REFUNDED`
