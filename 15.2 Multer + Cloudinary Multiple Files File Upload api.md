# File Upload with Multer + Cloudinary — Doctor Application (Multiple Files)

How a single request uploads a resume, multiple supporting documents, and structured form data (name, specialization, license number, etc.) all at once, and how that ends up stored in Postgres + Cloudinary.

---

## 1. Core Concepts (read this before the code)

### Why this needs `multer.memoryStorage()`, not disk storage
Multer can save uploaded files to disk (`diskStorage`) or hold them in RAM as a `Buffer` (`memoryStorage`). Since the end destination for these files is Cloudinary — not your own server's filesystem — there's no reason to write them to disk first just to immediately read them back and re-upload elsewhere. `memoryStorage()` gives you `file.buffer` directly, which you can stream straight to Cloudinary without ever touching disk.

### Why the route uses `upload.fields([...])`, not `upload.single(...)` or `upload.array(...)`
These are the three multer options, and each fits a different shape of request:
- **`upload.single("fieldName")`** — exactly one file, one field name. Fine for a single profile picture.
- **`upload.array("fieldName", maxCount)`** — multiple files, but all under the *same* field name (e.g. a gallery upload where every file is named `photos`).
- **`upload.fields([...])`** — multiple *different* field names, each with its own file (or set of files). This doctor application needs exactly this: one field called `resume` (max 1 file) and a separate field called `additionalFiles` (max 10 files) — two different kinds of documents, uploaded together in one request.

### Why form data (not raw JSON) for this endpoint
A request with files can't be sent as `Content-Type: application/json` — files need `multipart/form-data`. But your structured fields (name, specialization, license number, etc.) still need proper types and validation, which don't survive well as flat form fields on their own (multipart form fields naturally arrive as strings, so a number field would arrive as `"5"` instead of `5`).

**The pattern used here:** the frontend sends one form field called `data`, containing the *entire* structured payload as a JSON string, alongside the actual file fields (`resume`, `additionalFiles`). The backend does `JSON.parse(req.body.data)` to get real, nested JSON back, then runs it through Zod — this is what lets `ApplyAsDoctorValidationZodSchema` validate a proper `{ user: {...}, doctor: {...} }` object instead of trying to make sense of flattened form fields.

### Why `cloudinary.uploader.upload_stream` is wrapped in a `Promise`
Cloudinary's `upload_stream` is callback-based, not Promise-based, by default — it takes a callback function that fires once the upload finishes. Wrapping it in `new Promise((resolve, reject) => {...})` lets you `await` it like any other async operation, which is what makes it possible to write `const resumeUploadResult = await ...` instead of nesting everything inside callbacks.

### Why `additionalFiles` uses `Promise.all(...map(...))` instead of a `for` loop
Uploading files to Cloudinary one at a time, sequentially, would mean each file waits for the previous one to finish — slow if someone attaches 10 files. `Promise.all` fires all the upload requests **at the same time**, and only continues once every single one has resolved (or immediately rejects if any one fails). Same total work, far less wall-clock time.

### Why `resume` and `resumePublicId` are stored as two separate fields, but `additionalFiles` is one `Json` field
The resume is a single, known file — a plain `String?` column for its URL (plus a second column for its Cloudinary `public_id`, needed later if you ever want to delete or replace it) is simple and directly queryable. `additionalFiles` is a *variable-length list* of files — rather than creating a whole separate table just to hold "file 1, file 2, file 3...", storing them as a JSON array (`[{ url, publicId }, ...]`) directly on the `Doctor` row is simpler here, since these files are always fetched and displayed together as a set, never queried individually.

### Why `verificationStatus` defaults to `PENDING`
A doctor application isn't automatically a verified doctor — someone (an admin) needs to review the resume/credentials first. `PENDING` → `APPROVED`/`REJECTED` is a manual admin gate, tracked via `reviewedBy`/`reviewedAt`/`rejectionReason`, separate entirely from whether the user account itself was successfully created.

### Why this creates both a `User` and a `Doctor` row together, in one nested `create`
Same pattern as any "extend the base account with role-specific data" design — a `User` row handles login/auth, a `Doctor` row holds everything specific to being a doctor (specialization, resume, license). Creating both in a single `prisma.user.create({ data: { ..., doctor: { create: {...} } } })` call means either both rows get created together, or (if something fails) neither does — no risk of a `User` existing with no matching `Doctor` profile.

### Why a random password gets generated instead of the doctor choosing one at signup
This is an application flow, not a self-registration flow — a prospective doctor is applying to join the platform, not creating their own account from scratch. Generating a temporary password (paired with `needPasswordChange: true`) means once an admin approves the application, the doctor can log in with the temporary credentials and immediately gets prompted to set their own real password.

## 2. Schema

```prisma
model Doctor {
    id String @id @default(uuid())

    name    String
    email   String  @unique
    address String?

    specialization  String
    licenseNumber   String @unique
    qualifications  String
    experienceYears Int

    bio             String?
    consultationFee Decimal? @db.Decimal(10, 2)

    contactNumber String?

    verificationStatus DoctorVerificationStatus @default(PENDING)
    rejectionReason    String?
    reviewedBy         String?
    reviewedAt         DateTime?

    resume          String?
    resumePublicId  String?
    additionalFiles Json? // Array of file URLs or file metadata // Stores: [{ url: "...", publicId: "..." }]

    isDeleted Boolean   @default(false)
    deletedAt DateTime?

    createdAt DateTime @default(now())
    updatedAt DateTime @updatedAt

    userId String @unique
    user   User   @relation(fields: [userId], references: [id], onDelete: Cascade, onUpdate: Cascade)

    @@index([email], name: "idx_doctor_email")
    @@map("doctors")
}

enum DoctorVerificationStatus {
  PENDING
  APPROVED
  REJECTED
}
```

## 5. Controller

```typescript
// doctor.controller.ts
import type { Request, Response } from "express";
import httpStatus from "http-status";
import { catchAsync } from "../../utils/catchAsync";
import { sendResponse } from "../../utils/sendResponse";
import { DoctorServices } from "./doctor.service";
import { ApplyAsDoctorValidationZodSchema } from "./doctor.validation";

const applyAsDoctor = catchAsync(async (req: Request, res: Response) => {
	const files = req.files as { [fieldname: string]: Express.Multer.File[] };
	console.log({ files });
	const resume = files?.["resume"] ? files["resume"][0] : null;
	const additionalFiles = files?.["additionalFiles"] || [];

	const zodValidationResult = ApplyAsDoctorValidationZodSchema.safeParse(
		JSON.parse(req.body.data),
	);

	if (!zodValidationResult.success) {
		throw new Error(zodValidationResult.error.issues[0].message);
	}

	const payload = zodValidationResult.data;

	const result = await DoctorServices.applyAsDoctor(
		payload,
		resume,
		additionalFiles,
	);
	sendResponse(res, {
		statusCode: httpStatus.OK,
		success: true,
		message: "Applied As Doctor Successfuly",
		data: result,
	});
});

export const DoctorController = {
	applyAsDoctor,
};
```

## 6. Service — where the actual uploads happen

```typescript
// doctor.service.ts
import bcrypt from "bcryptjs";
import type { UploadApiResponse } from "cloudinary";
import { Role } from "../../../generated/prisma/enums";
import config from "../../config";
import { cloudinary } from "../../lib/cloudinary";
import { prisma } from "../../lib/prisma";

const applyAsDoctor = async (
	payload: any,
	resume: Express.Multer.File | null,
	additionalFiles: Express.Multer.File[],
) => {
	const isUserExists = await prisma.user.findUnique({
		where: {
			email: payload.user.email,
		},
	});

	if (isUserExists) {
		throw new Error("User Already Exists With This Email");
	}

	const resumeUploadResult = await new Promise<UploadApiResponse>(
		(resolve, reject) => {
			cloudinary.uploader
				.upload_stream(
					{
						resource_type: "auto",
					},

					async (error, result) => {
						if (error) {
							return reject(error);
						}

						if (!result) {
							return reject(new Error("No result returned from Cloudinary"));
						}

						resolve(result);
					},
				)
				.end(resume?.buffer);
		},
	);

	console.log({ resumeUploadResult });

	const additionalFilesUploadResults = await Promise.all(
		additionalFiles.map((file) => {
			return new Promise<UploadApiResponse>((resolve, reject) => {
				cloudinary.uploader
					.upload_stream(
						{
							resource_type: "auto",
						},

						async (error, result) => {
							if (error) {
								return reject(error);
							}

							if (!result) {
								return reject(new Error("No result returned from Cloudinary"));
							}

							resolve(result);
						},
					)
					.end(file.buffer);
			});
		}),
	);

	console.log({ additionalFilesUploadResults });

	const randomDoctorPassword = Math.random().toString(36).slice(-8);

	const hashedPassword = await bcrypt.hash(
		randomDoctorPassword,
		Number(config.bcrypt_salt_rounds),
	);

	const doctorApplication = await prisma.user.create({
		data: {
			...payload.user,
			password: hashedPassword,
			role: Role.DOCTOR,
			needPasswordChange: true,
			doctor: {
				create: {
					name: payload.user.name,
					email: payload.user.email,
					...payload.doctor,
					resume: resumeUploadResult.secure_url,
					resumePublicId: resumeUploadResult.public_id,
					additionalFiles: additionalFilesUploadResults.map((file) => ({
						url: file.secure_url,
						publicId: file.public_id,
					})),
				},
			},
		},

		include: {
			doctor: true,
		},
	});

	return doctorApplication;
};

export const DoctorServices = {
	applyAsDoctor,
};
```

## 7. Validation

```typescript
// doctor.validation.ts
import { z } from "zod";

export const ApplyAsDoctorValidationZodSchema = z.object({
	user: z.object({
		name: z.string().trim().min(2, "Name must be at least 2 characters long"),

		email: z.email("Invalid email address").trim().toLowerCase(),
	}),

	doctor: z.object({
		address: z
			.string()
			.trim()
			.min(5, "Address must be at least 5 characters long")
			.optional(),

		specialization: z.string().trim().min(2, "Specialization is required"),

		licenseNumber: z.string().trim().min(3, "License number is required"),

		qualifications: z.string().trim().min(2, "Qualifications are required"),

		// Handles converting incoming FormData strings like "12" into an integer number
		experienceYears: z
			.number()
			.int("Experience years must be an integer")
			.min(0, "Experience years cannot be negative")
			.optional(),

		bio: z
			.string()
			.trim()
			.max(1000, "Bio cannot exceed 1000 characters")
			.optional(),

		// Handles converting incoming FormData strings like "150.00" into a float number
		consultationFee: z
			.number()
			.min(0, "Consultation fee cannot be negative")
			.optional(),
		contactNumber: z
			.string()
			.trim()
			.min(5, "Contact number is invalid")
			.optional(),
	}),
});
```

## 8. The whole flow, end to end

1. Frontend builds a `multipart/form-data` request with three parts: a `data` field (JSON-stringified `{ user, doctor }`), a `resume` file, and 0–10 `additionalFiles`
2. `upload.fields([...])` (multer) parses the multipart body, splitting out `req.files.resume` and `req.files.additionalFiles`, leaving `req.body.data` as the raw JSON string
3. Controller extracts the files, `JSON.parse`s `req.body.data`, and validates the result against `ApplyAsDoctorValidationZodSchema`
4. Service uploads the resume to Cloudinary (single `upload_stream`, wrapped in a `Promise`)
5. Service uploads every additional file **in parallel** (`Promise.all`)
6. Service creates one `User` row and one nested `Doctor` row in a single `prisma.user.create(...)` call, storing the Cloudinary URLs/public IDs from steps 4–5
7. Application sits at `verificationStatus: PENDING` until an admin reviews it

## 9. Worth double-checking before this goes further

A few things in the current code are worth a second look — not rewritten here since the code above is your working reference, just flagging for when you're ready:

- **`resume?.buffer` when `resume` is `null`** — the route doesn't currently enforce that a resume file is required, but the service always tries to upload it (`.end(resume?.buffer)` would pass `undefined` to Cloudinary if no resume was attached). Worth deciding: should resume be mandatory at the route/validation level, or should the upload step skip entirely when `resume` is `null`?
- **No cleanup if `prisma.user.create` fails after uploads succeed** — if the resume and additional files upload successfully to Cloudinary, but the database write then fails (e.g. a duplicate license number), those files stay orphaned in Cloudinary with nothing in your database referencing them. Worth deciding whether that's acceptable for now, or whether failed applications should trigger a `cloudinary.uploader.destroy(...)` cleanup pass.
- **`needPasswordChange` and `doctor` as a relation name on `User`** — make sure these actually exist on your `User` model as written; this note only covers the `Doctor` side of the schema.
